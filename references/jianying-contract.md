# 剪映草稿的硬约束与排错

## 写入链路

草稿由 `~/.codex/skills/jianying-editor` 的 `JyProject`（底层是 `pyJianYingDraft`）直接写
`draft_info.json`。写入的是**明文工程**，剪映能读；剪映一旦打开这个草稿并保存，就会把它重新
保存成自己的加密格式（文件变大，多出 `Timelines/`、`Resources/`、`.locked`）。

由此有三条操作规则：

1. **不要在剪映保存过之后再解析 `draft_info.json`。** 拿不回素材路径，需要素材清单就从 plan 推。
2. **打包必须在剪映关闭时做**，否则会复制到写了一半的目录，对方打开报"草稿内容已损坏"。
3. 剪映重新保存是正常行为，不是坏了，不要试图还原明文。

## 轨道与时间

- 同一轨道**不允许重叠**，否则抛 `SegmentOverlap`。相邻片段要用上一段的真实结束点接续：
  播放器按"源长度 ÷ 速度"以微秒重算时长，而编排表是毫秒取整，差几百微秒就会判重叠。
- 累计显示的图卡（01/02/03/04 一行行加上去）必须**各占一条文字轨**，否则后一条覆盖前一条。
- 标题、落版、字幕同样各自独立成轨，方便对方单独开关和改样式。

## 文字定位

- `ClipSettings.transform_y` 的单位是"半个画布高"，**向上为正**。放画面上方用正值，下方用负值。
  与常见屏幕坐标相反，写反不会报错，只会上下颠倒。
- 字号是剪映自己的单位：1080 宽画布下 `size=7.0` 约等于 58px 正文，`9.5` 约 78px 标题。
  换到 1920 宽画布时不用把字号翻倍，保持视觉高度接近即可。
- 竖屏靠 `transform_y` 上下分区；横屏是左对齐布局，垂直位置仍用 `transform_y`。

## 画幅

画布由 `JyProject(name, width=…, height=…)` 决定：竖屏 1080×1920，横屏 1920×1080。
16:9 原片放进竖屏工程默认是"适应"（上下留黑），要铺满得放大；
竖屏铺满或画面带的取景应该在生成阶段按 `plan.meta.canvas` 算好。

## 打包与分发

草稿里的素材是**绝对路径**引用（导入方式是"保留在原有位置"），所以：

- 只发草稿文件夹，对方打开全是素材丢失；
- 正确做法是「草稿 + 一个扁平素材文件夹 + 导入说明」一起发；
- 对方把草稿放进自己的草稿目录，打开后点"重新链接"选中素材文件夹，剪映按文件名自动匹配，
  一次就能全部找回。素材文件名唯一是关键。

## 版本

- 本链路在剪映专业版 **11.4** 实测通过，生成时写入的 `new_version` 是 `110.0.0`。
- 5.x / 6.x 读不了这个格式；CapCut 国际版和手机端剪映不支持。
- macOS 上不支持自动导出。要 mp4 请在剪映里手动导出；这条链路只负责把**工程**做出来。

## 常见报错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `SegmentOverlap` | 毫秒取整与播放器重算时长打架 | 用上一段真实结束点接续（脚本已处理） |
| 打开提示"草稿内容已损坏" | 剪映开着时目录被替换或复制 | 关掉剪映，重新生成或复制 |
| 打开后素材全丢 | 只发了草稿没带素材 | 连素材一起发，重新链接素材文件夹 |
| 文字上下颠倒 | `transform_y` 符号写反 | 上方用正值 |
| 图卡只看到最后一条 | 多条图卡挤在同一轨 | 每条一行，各自分轨 |
| 草稿列表里时长显示 00:00 | 剪映还没解析过这个草稿 | 打开一次即恢复正常 |
